# AGENTS.md — Архив Терпения

## 1. Роль

Ты работаешь над проектом «Архив Терпения».

Твоя задача — создавать не демонстрационный код, а минимально работающий,
проверяемый и расширяемый продукт.

Работай как инженерный агент.

Главный принцип:

> Сначала доказать необходимость → затем реализовать минимальное решение
> → проверить → только потом усложнять.

---

## 2. Главная цель проекта

Создать Telegram-приложение, которое принимает информационные материалы
и превращает их в структурированный, проверенный и потенциально
монетизируемый результат.

Основной pipeline:

Telegram
↓
Input
↓
Normalize
↓
Classify
↓
Analyze
↓
Quality Gate
↓
Monetization Analysis
↓
Save
↓
Output

---

## 3. MVP

Первая рабочая версия должна:

1. запускаться на VPS;
2. работать через Telegram;
3. принимать текст;
4. сохранять исходный материал;
5. передавать материал в LLM;
6. получать структурированный анализ;
7. сохранять результат в SQLite;
8. возвращать результат пользователю;
9. переживать перезапуск процесса без потери данных.

После этого добавляются изображения, документы и другие источники.

---

## 4. Ограничения инфраструктуры

Целевая инфраструктура:

- 2 CPU;
- 2 GB RAM;
- 32 GB SSD;
- без GPU;
- Linux;
- Python;
- virtual environment;
- Telegram;
- OpenRouter;
- SQLite.

Не проектировать систему под GPU или большой сервер.

- Redis;
- Kafka;
- Elasticsearch;
- отдельную vector database;

4. оценить стоимость;
5. оценить нагрузку;
6. остановиться перед внедрением и запросить подтверждение.

---

## 6. Принцип минимальности

Перед созданием нового компонента проверить:

1. Есть ли уже такой компонент?
2. Можно ли переиспользовать существующий код?
3. Можно ли решить задачу стандартной библиотекой Python?
4. Можно ли использовать уже установленную зависимость?
5. Можно ли решить задачу одной функцией?
6. Действительно ли новая библиотека необходима?

Не создавать код ради архитектурной красоты.

Но минимальность не означает отказ от:

- безопасности;
- валидации;
- обработки ошибок;
- тестирования;
- сохранения данных;
- логирования.

---

## 9. Секреты

Секреты никогда не должны попадать:

- в исходный код;
- в Git;
- в README;
- в логи;
- в Telegram;
- в сообщения Roo;
- в тестовые fixtures.

Использовать `.env`.

Минимальные секреты:

TELEGRAM_TOKEN
OPENROUTER_API_KEY

Никогда не выводить их значения.

---

## 10. Telegram

bot.py отвечает за Telegram-интерфейс.

Он не должен содержать:

- SQL-логику;
- длинные prompts;
- бизнес-логику;
- прямые HTTP-вызовы OpenRouter.

Использовать разделение:

Telegram
↓
Pipeline
↓
Provider
↓
Database

---

## 11. Database

Для MVP использовать SQLite.

База должна сохранять исходные материалы независимо от успешности
LLM-обработки.

Ошибка LLM не должна уничтожать исходный материал.

---

## 12. LLM

LLM вызывается через отдельный provider layer.

Остальная система не должна зависеть от конкретной реализации HTTP API.

Если OpenRouter будет заменён другим provider,
pipeline должен потребовать минимальных изменений.

---

## 13. Ошибки

Внешние системы считаются ненадёжными:

- Telegram;
- OpenRouter;
- filesystem;
- SQLite.

При ошибке:

1. сохранить вход;
2. сохранить статус ошибки;
3. записать безопасный лог;
4. не сообщать пользователю ложный успех;
5. дать возможность повторной обработки.

---

## 14. Quality Gate

LLM не является абсолютным источником истины.

Результаты должны различать:

FACT
INFERENCE
ASSUMPTION
UNKNOWN

Если уверенность недостаточна:

confidence < threshold

материал не должен автоматически считаться проверенным.

Использовать раздел:

«На рассмотрении».

1. проверить syntax;
2. запустить соответствующие тесты;
3. проверить импорт;

что код выглядит правильным.
