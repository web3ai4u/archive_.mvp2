# Аудит MVP системы "Архив Терпения"

## 1. Текущая структура репозитория

На текущем снимке репозитория проект выглядит как заготовка/набор инструкций, а не как рабочий MVP. Основные элементы:

- `AGENTS.md` — правила и требования по проекту.
- `.github/copilot-instructions.md` — рабочий режим для GitHub Copilot и требования к Telegram/LLM/архиву.
- `IMPLEMENTATION_PLAN.md` — план реализации MVP.
- `README.txt` — краткая инструкция по работе с пакетами/промптами для агента.
- `requirements.txt` — минимальный набор зависимостей.
- `.gitignore` — базовые игнорируемые файлы.
- `.github/workflows/alibabacloud.yml` — шаблон GitHub Actions для Alibaba Cloud, не привязанный к текущему проекту.
- `prompts/` — четыре файла с заданиями для аудита/реализации/безопасности/деплоя.
- `.roo/rules/` — служебные правила локального агента, среди которых есть дубли.

Существенно: в текущем репозитории отсутствуют рабочие Python-модули, директории `src/`, `app/`, `bot/`, `storage/`, `logs/`, `tests/`, а также стандартные файлы запуска (`main.py`, `app.py`, `bot.py`, `manage.py`, `pyproject.toml`, `setup.cfg` и т.п.).

## 2. Рабочий Telegram entrypoint

В текущем состоянии рабочий entrypoint отсутствует.

Проверка по содержимому репозитория показала отсутствие:

- `main.py`
- `app.py`
- `bot.py`
- `__main__.py`
- `src/` или `package/`
- HTTP-обработчика и Telegram handlers

Следовательно, бот не может быть запущен в текущем состоянии, и не существует единого места, где:

- создаётся Application/Updater;
- регистрируются handlers;
- читаются переменные окружения;
- запускается polling/long-polling loop.

## 3. Что уже работает

На уровне репозитория уже есть несколько полезных частей:

- описан проект и требования в `AGENTS.md`;
- есть план реализации в `IMPLEMENTATION_PLAN.md`;
- зафиксированы обязательные переменные окружения в инструкции;
- `requirements.txt` задаёт базовый стек для Telegram и HTTP-клиента;
- `.gitignore` исключает `.env`, `venv`, `__pycache__`, логи и данные SQLite;
- существует базовый CI шаблон GitHub Actions.

Но это не рабочая сборка. Ни один из требуемых сценариев не подтверждён запуском, тестами и реальным кодом.

## 4. Ошибки и дубли

### Критические проблемы

1. Нет рабочего кода.
   - Репозиторий не содержит реализации Telegram-модуля, LLM-адаптера, схем, архиватора и тестов.

2. Нет entrypoint.
   - Нет файла запуска и точек входа для бота.

3. Нет файла конфигурации `.env.example`.
   - В инструкции прямо сказано создать `.env.example`, но его нет.

4. Нет README.md.
   - Есть `README.txt`, но в проекте по требованиям должен быть полноценный `README.md` с инструкцией запуска.

5. Нет `storage/` и `logs/`.
   - По `AGENTS.md` разделы архива и логи должны существовать, но директории не созданы.

6. Нет `tests/` и кодовых тестов.
   - Хотя AGENTS.md требует тесты для карточки и LLM-обработки, в репозитории нет ни одного тестового файла.

7. Нет привязки к Python 3.11+.
   - Не указан `python_requires`, не указана версия в CI, нет `pyproject.toml` или `.python-version`.

8. Неподходящий CI шаблон.
   - `.github/workflows/alibabacloud.yml` является общим шаблоном для Kubernetes/Alibaba Cloud, а не для Telegram MVP. Он не относится к проекту и не проверяет Python/бота.

9. Отсутствует LLM-адаптер.
   - В требованиях должен быть отдельный модуль для OpenRouter, но его нет.

10. Нет безопасной обработки файлов/архива.
   - Нет вычисления безопасного имени файла, нет хранения карточек в Markdown, нет логики `review`-каталогов.

### Дубли и мусор

- `.roo/rules` содержит повторяющиеся файлы `01-project.md`, `02-architecture.md` и несколько близких по смыслу правил.
- В проекте есть несколько документов с инструкциями, но отсутствует единый связанный набор исходников. Это делает репозиторий аморфным и затрудняет реализацию по чистой архитектуре.
- `README.txt` выглядит как инструкция для пакета/заготовки, а не как документация проекта.

## 5. Версии Python и библиотек

### Python

- Явная версия Python в репозитории не указана.
- Нет `pyproject.toml`, `poetry.lock`, `requirements-dev.txt`, `.python-version`, `Dockerfile` или CI, где бы ставилась версия `3.11` или выше.

### Библиотеки

`requirements.txt` содержит:

- `python-telegram-bot`
- `python-dotenv`
- `httpx`

Это минимальный базовый набор, но:

- версии не зафиксированы;
- отсутствует линтер/pytest;
- отсутствует `pytest` и `pytest-asyncio`/другие зависимости для тестов;
- нет явного ограничения для стабильной работы на Ubuntu VPS.

## 6. Наличие секретов в Git

По текущему видимому содержимому репозитория (целевому снимку Git) не найдено явных реальных токенов, ключей или секретов. В файлах нет видимых API-ключей, токенов Telegram или OpenRouter.

Однако:

- в проекте нет официальной политики секретов и их хранения;
- `.env` отсутствует, но `.env.example` тоже отсутствует;
- нельзя считать, что репозиторий безопасен в целом без дополнительной проверки истории Git, pre-commit hooks и секрет-сканеров.

Важно: в рамках аудита не следует раскрывать или читать реальные секреты, даже если они есть в истории; поэтому оценка здесь ограничена видимой рабочей копией и файлами Git.

## 7. Совместимость с Ubuntu VPS без GPU

По текущему состоянию проект не совместим с Ubuntu VPS без GPU по причине отсутствия рабочей реализации.

Но архитектурно проект выглядит совместимым с CPU-only VPS, потому что:

- Telegram-бот может работать на обычном Ubuntu;
- OpenRouter API вызывается по HTTP, без локального GPU;
- простая Python-оболочка и один процесс достаточно для MVP.

Для реальной совместимости потребуется:

- Python 3.11+;
- чёткий entrypoint;
- `.env.example` и запуск по `python main.py` или через systemd;
- логирование в `logs/`;
- хранение архива в `storage/`;
- корректная работа без GPU;
- мониторинг и graceful shutdown.

## 8. Вывод аудита

Текущий репозиторий — это не рабочий MVP, а набор инструкций и планов. Реализованный код фактически отсутствует. Основные бизнес-обязательства проекта (Telegram, OpenRouter, карточки, архив, тесты, безопасные имена файлов) пока не выполнены.

## 10. Необходимые файлы

Для реализации MVP необходимы минимум:

- `main.py` или `app.py` — Telegram entrypoint;
- `config.py` или `settings.py` — чтение `.env`;
- `llm_client.py` — отдельный адаптер к OpenRouter;
- `schemas.py` — модели и валидация карточки;
- `archive_processor.py` — обработка карточек, Markdown и разделов архива;
- `storage/` с директориями: `inbox/`, `archive/`, `review/`;
- `logs/` для журналов;
- `tests/` с минимальными сценариями;
- `.env.example`;
- `README.md` с инструкцией запуска;
- `requirements.txt` с фиксированными версиями и `pytest`.

## 11. Один следующий шаг

Следующий шаг: реализовать минимальный рабочий skeleton проекта по правилам из `AGENTS.md` и `IMPLEMENTATION_PLAN.md`, начиная с запуска Telegram-бота и чтения `.env`, без рефакторинга и без добавления лишней инфраструктуры.

То есть первым реальным действием должно быть создание базового entrypoint и минимального набора модулей (`config.py`, `main.py`, `.env.example`), после чего можно переходить к LLM-адаптеру и тестам.

## Итог

На этом этапе проект находится в состоянии документационного заготовки, а не рабочей реализации. Для перехода к реальному MVP нужен именно первый рабочий код, а не ещё один аудит документации.
