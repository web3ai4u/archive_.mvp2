# AGENTS.md

## Назначение проекта

Это минимальный MVP системы «Архив Терпения».

Проект принимает материалы через Telegram, анализирует их с помощью LLM и сохраняет результат в виде структурированных русскоязычных карточек архива.

Главная цель текущего этапа — надежный работающий MVP, а не сложная агентная платформа.

## Главные правила

1. Сначала изучи существующий код и структуру репозитория.
2. Не переписывай проект целиком без необходимости.
3. Не добавляй сложные технологии без доказанной потребности.
4. Не добавляй Docker, Redis, PostgreSQL, Celery, Kubernetes или векторную базу данных на первом этапе.
5. Используй Python standard library там, где это разумно.
6. Не изменяй секреты и не создавай реальные API-ключи.
7. Никогда не записывай API-ключи, токены и пароли в код.
8. Не изменяй файлы `.env`, если это не требуется для создания `.env.example`.
9. Не удаляй существующие функции без объяснения причины.
10. Перед изменением проверь совместимость с текущей версией Python и установленными библиотеками.
11. Все новые функции должны иметь понятную обработку ошибок.
12. Исходный код не должен содержать эмодзи.
13. Комментарии и сообщения для пользователя должны быть на русском языке, если это не техническое имя.
14. Имена переменных, функций и файлов должны быть на английском языке.
15. Не используй неявные глобальные состояния, если можно передать зависимость явно.
16. Не добавляй фоновую автономную публикацию без отдельного подтверждения владельца.
17. Не отправляй материалы во внешние сервисы, кроме явно настроенного LLM-провайдера.
18. Не выполняй опасные команды на сервере.
19. Не меняй настройки VPS, firewall, SSH и systemd без отдельного согласования.
20. Не считай задачу выполненной, пока не пройдены проверки.

## Архивные разделы

Разрешены только следующие разделы:

1. Фреймворки промптов
2. Инструменты
3. Системы и схемы
4. Устарело / Потеряло силу
5. На рассмотрении

## Формат архивной карточки

Каждая карточка должна содержать:

- Раздел
- Название
- Тип
- Суть
- Как использовать
- Когда особенно полезно
- Нюансы и ограничения
- Оценка полезности
- Вердикт

## Ограничения на обработку материалов

При создании архивной карточки:

- не упоминать авторов;
- не упоминать никнеймы;
- не упоминать даты публикации;
- не упоминать Twitter или X;
- не копировать текст дословно;
- не сохранять элементы интерфейса;
- переводить и перерабатывать материал на русском языке;
- разделять несколько независимых идей на отдельные карточки;
- не добавлять неподтвержденные факты;
- не выдумывать ссылки и источники;
- если материала недостаточно, помещать его в «На рассмотрении».

## Приоритеты разработки

Приоритет 1:

- запуск Telegram-бота;
- прием текста;
- прием изображений;
- прием документов;
- вызов LLM;
- проверка ответа;
- сохранение Markdown;
- возврат результата пользователю.

Приоритет 2:

- повторная обработка;
- защита от дубликатов;
- ограничение размера файлов;
- базовая статистика;
- команда просмотра последних карточек.

Приоритет 3:

- поиск по архиву;
- embeddings;
- RAG;
- несколько специализированных агентов;
- автоматическая публикация;
- монетизация;
- веб-интерфейс.

## Требования к LLM

LLM должен возвращать структурированный JSON.

Если ответ невалиден:

1. записать ошибку в лог;
2. выполнить не более одной повторной попытки;
3. если повторная попытка не помогла — сохранить исходный материал в «На рассмотрении»;
4. сообщить пользователю, что материал принят, но требует проверки.

Нельзя без проверки сохранять произвольный текст LLM как готовую карточку.

## Работа с файлами

Используй следующие каталоги:

- `storage/inbox/` — исходные материалы;
- `storage/archive/` — готовые карточки;
- `storage/review/` — материалы, требующие проверки;
- `logs/` — журналы;
- `tests/` — тесты.

Не удаляй исходный материал после обработки.

## Проверки перед завершением

Перед завершением задачи необходимо:

1. проверить синтаксис Python;
2. проверить импорт модулей;
3. запустить тесты;
4. проверить запуск бота без реального токена;
5. проверить обработку невалидного ответа LLM;
6. проверить обработку отсутствующих переменных окружения;
7. проверить, что секреты не попали в Git;
8. показать список измененных файлов;
9. кратко объяснить, что сделано и что осталось.

## Формат отчета

В конце каждой задачи предоставь:

### Выполнено

Список завершенных изменений.

### Проверки

Команды и результаты проверок.

### Измененные файлы

Список файлов.

### Риски

Что может потребовать ручной проверки.

### Следующий шаг

Только один следующий рекомендуемый шаг.
